# 每日工作檢討（一日三省）

## 觸發條件
- daily-review cron（daily_review_20260731223233，每天 22:00）
- 使用者要求「工作檢討 / 反省 / 檢討報告」
- 任何 session 結束時若使用者明確要求檢討今日工作

## 核心原則（使用者 2026-08-06 原話）
> 「工作檢討不只是要加記錄 而且要妳每日回讀歷史記錄來反省後 吸收沉澱避免以後再犯」
> 「一日三省」出自《论语·学而》— 每天多次自我反省，提升品德與行為。

**寫報告 ≠ 完成檢討。** 沒有回讀歷史、沒有對照反省、沒有沉澱更新的報告只是流水帳，使用者明確不滿這種做法。

## 完整流程（5 步，缺一不可）

### Step 1：回讀歷史
- 列出 `/opt/data/obsidian-vault/Holographic/每日檢討/` 下所有 `*-工作檢討.md`
- **重點讀每一份的「## 經驗教訓」與「## 代碼修改錯誤清單」**
- 建立歷史錯誤模式清單（例：重複修 bug 不提高層次、跳過 code review、jsdom 假驗證、UI 按鈕位置、簡短問句誤解語境）

### Step 2：檢查今日
- cron 錯誤：`cat /opt/data/cron/jobs.json | python3 -c "import json,sys; d=json.load(sys.stdin); jobs=d.get('jobs',d); [print(j['id'],j.get('last_status',''),j.get('last_run_at','')) for j in jobs]"`
- git 歷史：`cd /opt/data/projects/bookmark-manager && git log --since="today" --oneline`（+ youtube-note-pipeline / taiwan-stock 等今日動過的 repo）
- session 錯誤：`session_search` 搜尋「錯誤 失敗 用戶糾正」

### Step 3：反省對照（核心，不可跳過）
將今日行為**逐條對照歷史教訓**：
- 今天是否重蹈了哪條歷史教訓？（例如：又在同一層次修 bug？又跳過驗證就交差？）
- 哪些歷史教訓今天確實做到了？（也要記，證明有在進步）
- 今天有沒有犯**新的**錯？提煉成新教訓

### Step 4：吸收沉澱
把「反覆出現 ≥2 次的錯誤模式」或「今天新學到的重要教訓」真正沉澱：
- **更新相關 skill**：`skill_manage(action='patch')` 把教訓加進該 skill 的 Pitfall / 教訓章節（例如 reload bug 教訓 → personal-bookmark-system）
- 值得長期記的 → 寫入 memory（保持精簡，用 batch operations 控制字數）
- 在報告「## 沉澱結果」章節記錄做了哪些更新

### Step 5：寫報告
保存到 `/opt/data/obsidian-vault/Holographic/每日檢討/YYYY-MM-DD-工作檢討.md`
- `chmod -R 777 <報告路徑>`（手機 Sync 才看得到）
- 回報使用者時附上完整檔案路徑
- **先檢查今日報告是否已被 daily-review cron（22:00）產出**：若已存在，不要重寫一份造成重複 — 讀取既有報告 → 用 patch 補登新發現（例：2026-08-07 手動補登 command override 結論）→ 再 chmod 777

## 注意
- 系統錯誤 = cron job 失敗、API 限流等；代碼錯誤 = 我改 code 過程中被使用者糾正的錯；兩者都要記錄
- **反省對照與沉澱結果是必填章節**，若無重蹈覆轍要明確寫「無」
- 歷史教訓清單會增長，每次全部掃過再對照，不要只看最近一天
- 報告檔是 markdown，不要用 JSON/其他格式

## 已知歷史教訓庫（2026-08-06 累積，供對照）
1. **修 2 次以上沒好 = 紅旗**：停下來質疑架構 + 測試方法本身（2026-08-06 reload bug 修 6 次，jsdom 綠燈是假象）
2. **前端驗證層級：真實瀏覽器 ≥ DOM 結構分析 > jsdom**（jsdom 不執行外部 script，測不出 htmx 觸發的 bug）
3. **改完 code 自己測試再回報**，不讓使用者當白老鼠
4. **流程紀律優先於交付速度**：debug skill 8 步 + code review 不可跳過
5. **簡短問句先確認語境**：「卡住了嗎」可能指 job 佇列也可能指功能討論（2026-08-05）
6. **照操作路徑驗證 UI**：從使用者實際順序逐站檢查，不能只看單一畫面（2026-08-05 清除按鈕案例）
7. **不要把「UI 自動化」當成「持久化」的解法**（2026-08-06 v9）：使用者要的持久化是「勾選狀態記得」，不是「reload 自動彈視窗」。任何「reload 後自動做某個可見動作」（彈窗、開側欄、跳轉）都要質疑是否符合使用者工作流 — v8 把「有勾選就自動開配置表格」當正式行為，使用者指正「勾選≠進佇列，reload 自動跑到工作佇列不正常」
8. **回歸測試可能固化錯誤行為**（2026-08-06 v9）：寫測試前先確認斷言符合**使用者定義的工作流**，不是符合目前 code 的行為。v8 的 browser_reload_test.js 斷言「reload 後 sidebar 自動開 + rows=2」= 把錯誤行為當預期寫死；v9 改成「勾選保留 + sidebar 不開」才對。code review 也可能抓出測試斷言本身就是錯的
